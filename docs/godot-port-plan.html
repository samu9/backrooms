Plan: a Godot (C#) port alongside the web version

The Backrooms, Level 0 · branch worktree-godot-port-plan · 2026-11-19 · plan only, nothing implemented yet

TL;DR
  • One repo, three clients of the same world: web (three.js, unchanged behaviour), godot (C#, desktop, installed) and the relay server (unchanged).
  • The world is a pure function of the seed, and the relay decides catches with the TypeScript solid(). So the C# generator must give the same output as the TypeScript one, bit for bit. shared/gen.ts stays the source of truth. A TS script dumps golden fixtures, and a plain dotnet test checks the C# port against them.
  • C# is split in two: Backrooms.Core (no Godot dependency: generation, chunk data, hunt rules, A*, entity AI, protocol) and Backrooms.Game (Godot: meshes, shaders, UI, net, sound). Core is unit-testable and can run the AI simulation headless.
  • The rendering stays custom: an unshaded .gdshader ports the analytic panel lattice lighting, the ray-marched shadows and the procedural materials. Godot's lights and shadow maps aren't used.
  • Temporary sound: C# renders a small set of sounds into AudioStreamWav buffers at startup. They play through AudioStreamPlayer3D on a bus with reverb and a low-pass filter, behind an ISoundscape interface so the real solution can replace it later. There are still no audio files.
  • 11 milestones, M0 to M10. Each ends with something you can run. M0 (reorganise the repo, no behaviour change) can merge on its own right away.

2. Architecture

Why split C# into two projects: Core has no using Godot, so the parity tests, the hunt rule tests and the 30-round AI simulation run with a plain dotnet test (fast, CI-friendly, no editor). The Godot project references Core with a normal <ProjectReference>.

3. Determinism & parity

This is the part that can't be approximate. Three implementations must agree:

WhereWhatWhy it matters
shared/gen.tshash3, zones, solid, ceilingAt, lightKind, findFree, rngthe web client renders it, and the relay uses it for line of sight on catches, exit placement and spawns
Core/Gen.csthe same functionsif one cell differs, a desktop player sees a wall where the server sees none (and vice versa), and desktop and web players in the same room see different worlds
.gdshader hash3panel flicker, tints, wallpaper noisevisual only, but it must match the C# light lattice, otherwise a lit panel gets a dark ceiling

Porting rules for the hash

// TS:  Math.imul(x, 374761393)  … (h ^ (h >>> 13))  … (h >>> 0) / 4294967296
// C#:  wrapping 32-bit arithmetic, exactly the same steps
public static double Hash3(int x, int y, int z) {
    unchecked {
        int h = x * 374761393 + y * 668265263 + (z + Seed * 1013) * -2048144777;
        h = (int)(((uint)h ^ ((uint)h >> 13))) * 1274126177;
        h ^= (int)((uint)h >> 16);
        return (uint)h / 4294967296.0;
    }
}
  • Floats: TS numbers are IEEE doubles, so C# uses double everywhere in Core (vnoise, zone warping, findFree's trigonometry). Use Math.Floor, never casts, for negative coordinates, and port the mod() helper literally.
  • Math.round: JS rounds .5 toward +∞. C#'s Math.Round uses banker's rounding by default. Use Math.Floor(x + 0.5) wherever the TS uses Math.round (findFree, the height quantisation in chunk.ts).
  • Trigonometry: Math.cos/sin can differ in the last ulp between V8 and .NET. findFree only rounds their result to an integer cell, so a mismatch is very unlikely, and the fixtures cover it anyway.
  • The rng() PRNG (mulberry32): port it with uint and check the first 64 outputs for a handful of seeds.
  • Random choices made by the relay (roles, exit) come from the server over the network. The client never recomputes them, so Math.random isn't a parity concern.

Golden fixtures

npm run gen:fixtures runs tests/parity/dump.ts, which writes tests/fixtures/gen-golden.json (committed, a few hundred KB, gzip if needed):

  • hash3 on 2,000 random triples, including negatives and extremes, for 3 seeds;
  • a solid bitmap and quantised ceilingAt over 4 windows of 256×256 cells per seed, chosen to cross zone borders and negative coordinates. They're stored as base64 bitsets;
  • zoneAt (type, S, off, h, rail) on a sparse grid, lightKind over a 64×64 lattice, findFree from 50 points, and the first values of rng;
  • the chunk outputs for 2 chunks (occupancy RGBA bytes, light texture bytes, and a hash of the greedy quad list). This catches bugs in the chunk builder too.

Core.Tests/GenParityTests.cs loads the file and compares, reporting the first mismatching cell. Rule for CLAUDE.md: any change to shared/gen.ts is made in Core/Gen.cs (and the shader hash if it changes) in the same commit, then npm run gen:fixtures && npm run godot:test.

5. Rendering in Godot

Level & prop shaders

  • shader_type spatial; render_mode unshaded, cull_back; (props: cull_disabled). Lighting, AO and shadows are computed in fragment() exactly like the GLSL, with output to ALBEDO as HDR (unshaded albedo can go above 1 in Forward+).
  • One shared level.gdshaderinc. prop.gdshader does #define PROP, then #includes it, replacing three.js defines.
  • hash3 with uint arithmetic, the same constants as the GLSL.
  • Per-chunk data: uOcc/uLights textures and their origins live in a per-chunk ShaderMaterial. Instance uniforms can't hold samplers, so it's one material per chunk, about 30 in total, which is fine.
  • Global data: uTime, uSeed, fog and quality become global uniforms (project shader globals). Global uniforms can't be arrays, so uEnt[4] becomes 4 vec4 globals ent0..ent3.
  • The textures use filter_linear and repeat_disable, with sampler hints matching the three.js settings (the occupancy texture is sampled linearly for soft AO).
  • Godot's fog, SSAO and SDFGI are off. The shader does its own fog, as on the web.

Post / camcorder

  • Bloom and tone mapping: WorldEnvironment glow (levels 1–2 + 4–5 ≈ the two-level bloom, HDR threshold ≈ the smoothstep(1.2, 3.5) bright pass) and tonemap_mode = ACES.
  • Camcorder: a full-screen ColorRect on a top CanvasLayer with a canvas_item shader reading hint_screen_texture. It does the grade, chroma bleed, aberration, tape jitter, grain, vignette, plus uDread/uHunter/uFade.
  • The ordering difference: the web grade runs before tone mapping, in HDR. Here it runs after. The yellow/olive grade constants will need re-tuning by eye against shots/hero-*.png. If that isn't enough, upgrade to a CompositorEffect (pre-tonemap, Forward+ only).
  • MSAA: Viewport.msaa_3d = 4x. Resolution scaling: scaling_3d_scale driven by the same frame-time controller (target ≈ 18 ms), and FSR 1 as an option.
  • Renderer: Forward+ (desktop only, so the Compatibility renderer isn't needed).

6. Temporary sound

Goal: the game isn't silent, and the gameplay cues (entity drone, heavy steps, panting, player footsteps) can be heard and placed in space. Fidelity comes later. Everything sits behind an interface, so the real solution replaces one class.

public interface ISoundscape {
    void Start(); void SetMuted(bool m);
    void Update(Vector3 pos, Vector3 fwd, IEnumerable<LightInfo> lights, float dt);
    void PlayerStep(float run); void Footstep(float x, float z, bool heavy = false);
    void Presence(string key, PresenceKind kind, float x, float z, float level = 1);
    void OwnBreath(float level); void EndFrame();
}

synthesised in real time (oscillators, noise, biquads)SoundBank.cs renders about 10 clips into AudioStreamWav (16-bit PCM) at startup, in C#: mains hum loop (60/120/180 Hz + noise), panel buzz loop, flicker crackle, 4 footstep variants, knock, slam, drone loop, breath loop, creak. Later options, to look at when we come back to this: Steam Audio GDExtension (HRTF + occlusion), a real-time AudioStreamGenerator synth in C#, or FMOD/Wwise. The interface stays the same whichever we pick.

7. Milestones

Each milestone is its own PR with commits split by concern. The web build has to stay green after every one.

M0 · Reorganise the repo (TS only)

The moves from §1. gen.ts goes to shared/, the web client goes to web/, and the root scripts are updated. No behaviour changes.

Done when: typecheck, npm test, the build, the relay serving dist/, and the smoke + solotest playwright runs all pass, and the screenshots match the old ones.

M1 · C# skeleton + generation parity

godot/ solution, Core, Core.Tests, an empty Godot Game project. Port Gen.cs and Rng. dump.ts + fixtures + GenParityTests.

Done when: dotnet test is green on every fixture, and a deliberately broken constant makes it fail.

M2 · Chunks & walking around (debug look)

ChunkData (occupancy/light bytes, greedy walls/ceilings, soffits) with a parity test against the chunk fixtures. ChunkManager streaming with a time budget on worker tasks. Player controller with the same collides(), run, noclip, and a flat-colour debug shader.

Done when: you can walk through a --seed=123 world with no hitches. The layout matches the web version from the same viewpoint, and the minimap tiles (from M6) line up later.

M3 · Level shader port

Materials (wallpaper, carpet, tiles, panels), lattice lighting, flicker and dead blocks, ray-marched soft shadows, AO, fog, quality setting. The prop shader variant.

Done when: side-by-side screenshots against the web at the same seed and viewpoint (viewpoint(k) ported) look the same before post-processing.

M4 · Props, doors to nowhere, stairs into the ceiling

Box templates, half-rendered and merged modes, the vertex-snap glitch, emissive props.

Done when: the prop placement per chunk is identical to the web (a fixture covers the spot list).

M5 · Post / camcorder

Environment glow + ACES, camcorder shader, V/H toggles, adaptive resolution, stats overlay (P).

Done when: it looks like the web screenshots after grade tuning, and holds 60 fps or more at 1080p on the target machine.

M6 · UI: menu, HUD, minimap, full map

Menu (seed, room, name, server URL, play alone + difficulty), toasts, minimap with zoom, full map with marks to reach, fullscreen, mouse capture, settings saved in user://settings.cfg.

Done when: every keyboard shortcut in the README works in Godot.

M7 · Multiplayer

Net.cs (same protocol), avatars, name tags, interpolation, fallback to single player when the relay isn't reachable.

Done when: a web player and a Godot player in the same room see each other in the right places, and their world maps are identical.

M8 · The Hunt + solo vs CPU

HuntRules.cs, PathFinder.cs, EntityAI.cs in Core with ported tests and the simulation. Client Hunt.cs: stamina, phasing, HUD, entities killing lights (the ent0..3 globals), dread grade, LocalNet.

Done when: the hunt and AI tests pass, the simulation's catch rates are within ±10 points of the TS ones, a mixed web + Godot multiplayer round plays to the end, and solo works offline.

M9 · Temporary sound

ISoundscape, SoundBank, TempSoundscape, buses (§6). K mutes.

Done when: the hum, buzzers, footsteps (own and other players'), and the entity drone and breath can be heard and are positioned in space.

M10 · Packaging & install

Export presets for Windows (x86_64) and Linux. App icon and name, --seed/--room/--server command-line args, version from package.json. Optional: an installer (Inno Setup on Windows, AppImage or tarball on Linux), and a GitHub Actions job that runs dotnet test + the TS tests, then exports builds on tags.

Done when: a fresh Windows machine can install the game, run it and join a room on the deployed relay.

8. Tooling & dev setup

Right now neither dotnet nor godot is installed in this WSL distro. Needed:

  • .NET 8 SDK (or newer, the one the chosen Godot release requires) in WSL, for dotnet build/test of Core and of the Godot project.
  • Godot 4.x .NET edition (the latest stable): the editor plus the export templates.
  • Godot generates .godot/, *.import, bin/ and obj/. Add them to .gitignore in M1.

9. Risks & gotchas

Generation drifts between TS and C#

This is the worst failure, because nothing visibly breaks: a desktop player just walks "through" a wall the server thinks is there and never gets caught. Mitigation: golden fixtures, the CLAUDE.md rule, CI running both test suites. Optional but cheap: on welcome, the client sends a hash of solid() over a fixed window, and logs a warning if it doesn't match a value baked into the build. That changes only the client, the server stays the same.

Chunk build hitches

About 9.2k solid() calls, plus the lattice and greedy meshing, per chunk. In C# that's sub-millisecond, but uploading the mesh and textures has to happen on the main thread. Keep the web's time-budgeted streaming and only upload N chunks per frame. The zone cache must be thread-safe (one instance per thread, or a ConcurrentDictionary).

The camcorder look differs because of tone-mapping order

See §5. Accept a re-tune, or move the grade into a CompositorEffect.

Unshaded HDR + glow

Godot's glow uses the HDR scene. Unshaded ALBEDO above 1.0 does reach it in Forward+, but check this early in M3/M5 with a single bright panel test scene before porting everything.

Maintaining two clients

Features added to one client won't appear in the other by magic. Proposal: shared/ + Core/ hold everything that's rules and world, and the clients only do presentation. A feature that touches rules lands in both in the same PR, while presentation-only features can diverge.

10. Open questions

Q1 · Where does the Godot editor run? (a) the Windows editor opening the project via \\wsl.localhost\…, which is simple but has slower file I/O and an unreliable file watcher; (b) the Linux editor inside WSL through WSLg, which uses the same filesystem as the CLI but makes GPU performance in WSLg hard to judge; (c) a separate Windows clone for Godot work. Recommendation: (b) for day-to-day work and tests, then check performance with a Windows export.
Q2 · Which platforms to install on? Windows only, or Windows + Linux (+ macOS, which needs signing)? This affects M10 only.
Q3 · Do web and desktop players share rooms? The plan assumes yes, for free, since it's the same protocol. If not, nothing changes except the parity test becomes less critical (it would still matter for solo-mode AI behaviour).
Q4 · Visual fidelity target: pixel-close to the web version, or "same spirit, free to use Godot features where they look better"? The plan assumes pixel-close for M3, which also makes regressions easy to spot.
